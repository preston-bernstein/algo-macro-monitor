## Changes made

- **Critical, previously-undetected data-loss bug, found independently by two agents.** feed-commons' `normalize_entry()` drops any RSS entry with no `<title>` element, even if a `<description>`/`<summary>` is present — with no fallback and no log line (`poll()` doesn't even report a skipped count). Today's code falls back to the summary when title is missing (`title = getattr(entry, "title", None) or getattr(entry, "summary", None)`), so those entries are currently captured. The original plan explicitly (and incorrectly) claimed these filters were "exactly" equivalent — corrected, documented as an accepted behavior change (can't be fixed locally without forking feed-commons or duplicating its normalization logic, both explicitly out of scope), and given the same pre-deploy spot-check treatment as the other two known behavior changes.
- **Critical dedup-key drift risk.** feed-commons strips whitespace from `link`; today's code doesn't. Since this repo's dedup key is `sha256(source + url)`, a historical row with incidental URL whitespace would hash differently on re-poll post-retrofit, silently producing a duplicate row and breaking the append-only guarantee. Added as a new risk area with its own pre-deploy spot-check (diff feed-commons' normalized links against the production `url` column for already-seen entries).
- **Critical safety-net regression fixed before it shipped.** The original plan's exception handling around `poll()` caught only `PollError`, narrowing the current code's broad `except Exception`. On an unattended systemd timer, any unanticipated exception from feed-commons (a bug, a future regression) would have propagated uncaught through the entire collection run, violating the file's own "never raises" invariant. Fixed with a belt-and-suspenders pattern — `except PollError` first, then a broader `except Exception` fallback — mirroring the same pattern already proven in the earlier fashion-monitor retrofit this session.
- **A live production smoke test would have silently gone permanently dark.** `tests/test_smoke_e2e.py` calls the soon-to-be-deleted `_fetch()` directly as a reachability probe, wrapped in a broad `except Exception: pytest.skip(...)`. Post-retrofit this becomes an `AttributeError`, caught by the same broad except — the test would skip forever with zero failure signal, regardless of real network reachability. Fixed: probe rewritten to call `poll()`, except-clause narrowed so only a genuine network-unreachable case skips; anything else fails loudly.
- **Three files outside the plan's stated integration points would have silently broken.** Direct grep found `tests/test_cli.py` (3 tests monkeypatching `_fetch` directly) and `src/macro_monitor/correlator.py` (a stale docstring reference to `_entry_date`) in addition to the smoke test above — none were named in the original plan's Integration points. All three added, with explicit steps to fix each.
- **Deploy-key risk, converged from three independent agents.** Nothing verified the desktop deploy host's `algo-macro` service user actually has SSH access to clone the private feed-commons repo — this exact failure class already happened once in this repo's own history for the `fleet-logging` dependency (a dedicated deploy-key fix was needed). Flagged explicitly as a pre-merge verification item, not assumed by analogy to fleet-logging's fix.
- **Lost diagnostic detail fixed.** The plan's `err_msg=str(exc)` for a caught `PollError` was pure duplication of `err_type` (verified: `PollError.__str__` is just the bounded code). Verified feed-commons does chain the original exception in at least one path (`raise PollError("network_error") from exc`) — fixed to use `str(exc.__cause__)` when present, preserving real diagnostic detail instead of discarding it.
- **Wrong SQL column name caught before it was ever run.** The pre-deploy HTTPS-check step assumed a `source_name` column; the real production `sources` table (confirmed via a live query this session) uses `name`. Fixed, and the pre-deploy spot-checks (HTTPS, parse-failure, title-fallback, dedup-drift) were all moved earlier in steps.md — right after the dependency is installed, before any code refactor — so a late-breaking regression surfaces before code work is sunk into it, not after.

## Critiques rejected

- **Invalid_url given differential severity/alerting treatment** (Design Devil's Advocate): explicitly, deliberately out of scope per requirements.md's own Out-of-scope section (all 5 PollError codes handled uniformly, by design, not oversight).
- **Commit-signature verification for the git+ssh pin** (Security Auditor): no existing precedent anywhere in this home-lab's git+ssh dependency pattern (fleet-logging, credential-crypto); inventing new supply-chain policy is out of scope for this task.
- **Retry/backoff layer, XXE test harness, rate-limit runbook** (Security Auditor): all explicitly out of scope per requirements.md, or (XXE) already a pre-existing characteristic of the current code's own direct `feedparser.parse()` call — not a new risk this retrofit introduces, noted as a one-line clarification only.
- **err_msg=str(exc) "could leak too much"** (Security Auditor): factually incorrect — verified `PollError`'s message body is bounded to just its 5-code taxonomy by construction; superseded by the opposite (and correct) finding that it discards too little detail, which was accepted and fixed instead.
- **Automated recurring gate for future-added sources, beyond the one-time pre-deploy spot-checks** (Scope Auditor): out of scope — the existing `PollError` → logged-failure path already gives ongoing visibility for future sources (any misconfigured or malformed future source shows up as a logged failure on its very next poll, not silently); building additional automated infrastructure for a single-source system is disproportionate.
- **Deploy step and rollback-for-bad-live-deploy in steps.md** (Scope Auditor, Implementation Realist, Steps Critic — 3 agents): correctly identifies this is a live system needing real deploy verification, but deploy and its rollback belong to a separate orchestration phase, not implementation steps — consistent with this session's established convention for this exact class of finding.

## Open questions requiring human input

None — every finding was either concretely fixable within this spec or explicitly scoped out with a stated reason above. No hard blockers (security, data loss with no mitigation, or ADR contradiction) remain unaddressed. The two real data-loss/data-integrity risks found (title-fallback drop, dedup-key drift) were spot-checked empirically before proceeding, not just documented as a future step: a live re-poll of the real production feed found 0 of 20 entries relying on the summary-title fallback, and a direct query of the production `raw_observations` table found 0 of 36 existing rows with URL whitespace that would drift the dedup key. Both are clear for the current production configuration; steps.md still carries these as standing pre-deploy spot-checks for when new sources are added later.
